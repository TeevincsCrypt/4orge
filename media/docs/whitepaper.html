Abstract

Deploying a smart contract is still assembled by hand from compilers, package managers, test runners, RPC endpoints, wallets, scripts, explorers and spreadsheets. Each hand-off is a chance to deploy the wrong code, to the wrong network, with the wrong arguments, or without tests.

4ORGE (pronounced Forge) is developer infrastructure for QIE Blockchain that replaces that pipeline with one guided, repeatable workflow. Projects come from templates, uploads or GitHub, and are analysed without ever executing their configuration. Contracts are compiled with integrity-checked official Solidity builds and tested with Hardhat 3 in a sandbox. Every deployment runs as a Runbook: a strict, versioned workflow made only of allowlisted steps, with no "run a command" step. It stops for exactly two things a person must do: review and sign in their own wallet. 4ORGE never sees a private key. After the wallet broadcasts, the server independently fetches the transaction and receipt from QIE and accepts the deployment only if the on-chain data matches what was reviewed, byte for byte.

4ORGE is built for QIE specifically: chain IDs are verified live, multiple RPC endpoints are tried with chain-ID proof, source code is verified on QIE's explorer, Mainnet is locked behind explicit operator opt-in and a typed confirmation, and address arguments accept QIE ID names (name.qie), resolved once and pinned. The system is live, and its first real deployment, AtlasGovernor, is on QIE Mainnet with verified source.

01The problem

A typical EVM release requires a developer to assemble and trust a chain of independent tools:

  • Toolchain setup: the right Solidity compiler version, framework, and dependencies such as OpenZeppelin, installed with package managers that run arbitrary install scripts.
  • Testing: run in a terminal, with no guarantee that what was tested is what gets deployed.
  • Network configuration: an RPC URL and chain ID copied from documentation; a wrong value silently targets the wrong chain.
  • Deployment scripts: written or copied per project, often holding a private key in an environment file.
  • Confirmation: a transaction hash scrolls past; success is assumed rather than verified.
  • Record-keeping: addresses pasted into spreadsheets or chat, with no link to the code, arguments or compiler that produced them.

The costs are concrete: deploying untested code, using wrong constructor arguments (owners, supplies), targeting the wrong network, losing track of what is deployed where, and exposing keys. For developers new to QIE, assembling this toolchain is the largest barrier to shipping anything at all.

Goal. Make the safe path the easy path: one workspace where every deployment is reviewed, repeatable, recorded and verified against the chain, with keys that never leave the user's wallet.

03System architecture

4ORGE is a Next.js 16 application with a versioned REST API (/api/v1) that the interface itself uses. Server-side services own all state transitions; the browser owns only the wallet.

Figure 1. Components and trust boundaries. Signing happens only in the browser wallet; all verification happens on the server against QIE.

Technology

  • Frontend: Next.js 16 (App Router), TypeScript, Tailwind CSS 4, a light responsive design system.
  • Blockchain: viem for RPC, encoding and wallet clients; EIP-1193/EIP-6963 wallet discovery; EIP-3085/3326 network add/switch.
  • Build and test: official soljson Solidity compilers; Hardhat 3 with EDR and the viem toolbox; a safe npm Solidity resolver.
  • Data: Supabase (Postgres, Row Level Security, email and GitHub sign-in) or a zero-configuration local mode.
  • Hosting: any Node.js server with a persistent disk; the reference deployment runs on Railway.

04Projects and untrusted input

Projects can start from a template (Counter, ERC-20, OpenZeppelin ERC-20, blank), be uploaded as a Hardhat or Foundry folder, or be imported from a public or private GitHub repository. All three paths treat the code as untrusted:

  • Static detection. hardhat.config.*, foundry.toml, remappings.txt and package.json are read as text to find the compiler version, optimizer, EVM target, remappings, dependencies and tests. Running a project's Hardhat config would mean executing arbitrary code on the server, so it never happens. Configs in a subfolder (for example a monorepo's contracts/foundry.toml) are found and their paths rebased.
  • Path safety. Every path is normalised and rejected if absolute or containing ..; only source, test and config file types are stored, with per-file and per-project size limits.
  • Streaming import. GitHub archives are streamed through the tar parser and only project files are kept, so a repository with large assets (up to 1 GB) costs download time, not memory or disk. Only regular files are read; symlinks and devices are skipped.

05Compilation

  1. Resolve sources. Imports are followed through relative paths, remappings and project files, then npm packages. Packages are fetched from the npm registry and verified against their SHA-512 integrity; only .sol and package.json files are extracted and no install script runs. forge-std, whose npm release is stale, comes from a pinned GitHub commit checked against a content hash.
  2. Choose the compiler. The configured version if it satisfies every pragma, otherwise the newest release satisfying all of them. Official builds are integrity-checked and cached.
  3. Compile in isolation. A separate Node process with a timeout, memory cap and scrubbed environment receives all sources up front, so the compiler never touches the filesystem. Large inputs are passed on the WebAssembly heap rather than its small stack, which removes a class of "memory access out of bounds" crashes on big Foundry test suites.
  4. Record everything. Errors, warnings, ABIs, bytecode and the exact Standard JSON input are stored. The same input is later used for explorer verification, so the verified bytecode matches.

06Sandboxed testing

Tests run with Hardhat 3 in a throw-away sandbox that 4ORGE builds for each run:

  • 4ORGE writes its own Hardhat configuration; the project's config is never executed. The compiler is the same cached build used for compilation.
  • node_modules links to a pinned runner toolchain and the integrity-checked packages. Hardhat runs with a timeout, heap cap, output cap, private HOME and no server secrets; the sandbox is deleted afterwards.
  • Solidity tests (*.t.sol, including Foundry-style forge-std suites with fuzz and invariant tests) execute inside the EVM and cannot touch the host. TypeScript tests are real code and run only where the operator allows it.
  • File access declared in foundry.toml (fs_permissions, for vm.readFile and similar) is honoured inside the sandbox, but write access is never granted to the sandbox root or library folders, which link to shared caches.
  • Results are parsed into per-test records (name, status, duration, failure message). A Runbook can require tests to pass before anything is deployed.

07Runbooks

A Runbook is a declarative workflow in the strict 4orge.runbook/v1 format, editable visually and exportable as JSON or YAML. Every deployment, including the one-click wizard, runs as a Runbook, so each one can be inspected, repeated and audited.

schema: 4orge.runbook/v1
name: Deploy Vault to QIE Mainnet
network: qie-mainnet
target: { contract: Vault, source: contracts/Vault.sol, constructorArgs: [ "alice.qie", "1000" ] }
steps:
  - { id: load,    uses: project.load }          - { id: confirm, uses: human.confirm }
  - { id: network, uses: network.check }         - { id: sign,    uses: wallet.deploy }
  - { id: compile, uses: contracts.compile }     - { id: receipt, uses: tx.confirm }
  - { id: test,    uses: contracts.test }        - { id: record,  uses: deployment.record }
  - { id: args,    uses: deploy.validate-args }  - { id: verify,  uses: contract.verify }
  - { id: prepare, uses: deploy.prepare }        - { id: report,  uses: report.generate }
StepCategoryResponsibility
project.load, project.validateAutomatedSnapshot files and structure; check sources, compiler and target.
network.checkAutomatedeth_chainId must match; locked networks fail here.
contracts.compile, contracts.testLocal buildCompile and record the build; run tests (required by default).
deploy.validate-argsAutomatedType-check arguments against the ABI; resolve and pin QIE IDs.
deploy.prepareAutomatedEncode creation data, estimate gas and fees, check balance.
human.confirmHumanPause for review (typed MAINNET on Mainnet).
wallet.deployWalletThe browser wallet signs and broadcasts. Never run by the server.
tx.confirm, deployment.recordAutomatedValidate the receipt on-chain; record the deployment.
contract.verify, report.generateAutomatedSubmit source verification; write a Markdown report.

Ordering rules enforce safe sequences beyond the schema: dependencies must come earlier, each step type appears once, and a wallet.deploy must be followed by tx.confirm and deployment.record, so a broadcast transaction is always confirmed and recorded. On Mainnet, a Runbook that deploys without a human.confirm step is rejected.

Execution model. Executions are server-authoritative state machines: clients can only ask the server to advance, confirm, retry, cancel or accept a wallet result, and the server checks that the step is actually waiting for that input. A per-execution lock prevents double execution. Failed steps can be retried when safe; a wallet step can never be retried once a transaction has been broadcast.

08Deployment and receipt validation

The deployment path is designed so that what the user reviews is exactly what is signed, and what is signed is exactly what is recorded.

  1. Prepare. The server encodes the creation data (compiled bytecode plus ABI-encoded constructor arguments), estimates gas and fees, and reads the deployer's balance from the chain.
  2. Review. A popup shows the contract, network and chain ID, deployer, arguments (with any QIE ID next to its pinned address), gas limit, maximum cost and balance. The step list stays visible while it is open.
  3. Sign. The wallet is switched to the right network if needed and asked to send exactly the prepared transaction. The hash is saved locally before it is reported and recorded as a pending deployment immediately, so a closed tab cannot lose a broadcast transaction.
  4. Validate on-chain. The server fetches the transaction and receipt from QIE and accepts the deployment only if all of the checks below hold.
CheckWhy it matters
The transaction is a contract creation (to = null)A hash of any other transaction cannot be passed off as a deployment.
Sender equals the approved deployerThe account that was reviewed is the account that deployed.
Input equals the prepared creation data, byte for byteThe deployed code and constructor arguments are exactly the reviewed ones.
Chain ID matches and receipt status is successNo cross-chain confusion; reverted deployments are failures.
Code exists at the new contract addressThe contract is really there.
Proven, not assumed. The end-to-end test deploys through a real browser and wallet against a real EVM, reads the deployed contract back, and then submits a forged transaction hash. 4ORGE rejects it: "Transaction is not a contract creation."

Mainnet safeguards

  • QIE Mainnet deployments are locked by default and require the operator to set FORGE_ENABLE_MAINNET_DEPLOYMENTS=true.
  • A Mainnet Runbook must contain a human review step; the wizard forces it on.
  • The server refuses to confirm the review unless the user types MAINNET; "real funds" warnings appear in the wizard, review and wallet step.

QIE ID: human-readable addresses, pinned before signing

QIE ID is QIE's identity layer: names such as alice.qie that point to wallet addresses. In 4ORGE, every constructor argument of type address (including address[] and tuple fields) accepts a 0x address or a QIE ID, freely mixed.

  • The form previews alice.qie → 0x… on the selected network as the user types.
  • The deploy.validate-args step resolves each name once through QIE's official QIE Wallet MCP resolver (tool qie_resolve_name, which reads the QIE ID contracts on chain) and pins the result.
  • deploy.prepare encodes only the pinned addresses and never resolves again, so a name repointed mid-deployment cannot change what is reviewed and signed. The review, wallet popup and report all show name.qie → 0x….
  • Only a well-formed, non-zero address is accepted from the resolver; an outage is an error, never "not registered".

10Security model

ThreatMitigation
Key theftNo keys are requested, stored or transmitted; signing happens only in the user's wallet.
Malicious repository or configConfigs are parsed as text, never executed; paths validated; only allowed file types stored; archives streamed and filtered.
Supply-chain tamperingnpm tarballs verified with SHA-512; compilers with published SHA-512/SHA-256; forge-std pinned to a commit and content hash; no install scripts.
Malicious RunbookStrict schema and a 13-step allowlist with no command execution; ordering validator; Mainnet requires review.
Forged or swapped transactionServer-side receipt validation against the prepared transaction (five checks); proven by the forged-hash test.
Wrong networkLive chain-ID checks on every RPC; wallet chain enforced at signing; Mainnet locked by default.
Name repointing (QIE ID)Resolve once, pin, show in review, never re-resolve during preparation.
Resource exhaustionSeparate processes with timeouts, memory and output caps; server-wide concurrency limit; download caps.
Cross-site requestsSame-origin check on state-changing API calls; security headers; zod-validated, size-limited bodies.
Data leakage between usersPostgres Row Level Security on every table, using the user's own JWT (no service-role key), plus an owner filter in the adapter.

Known limitation: process-level isolation suits single-user and trusted hosting. Multi-tenant hosting that runs untrusted TypeScript tests should place the test worker in a container or VM sandbox; the runner has a single boundary for that.

11Data, privacy and auditability

  • Two storage modes behind one interface: Supabase (multi-user, Postgres with Row Level Security, email and GitHub sign-in) or local mode (single user, data on the owner's machine, loopback-only API).
  • Ownership enforced in the database: owner-only policies on every table, and child rows can only reference parents the user owns. Tested against a real Postgres with two users.
  • Audit trail: deployment records cannot be deleted and survive project deletion. Each record keeps the network, chain ID, deployer, address, transaction, block, gas, compiler, constructor arguments and verification status, with explorer links.
  • GitHub access: an OAuth token stored only in an AES-256-GCM encrypted, httpOnly cookie, never in the browser or the database.

13Roadmap

  • QIE ID everywhere: show QIE IDs for deployers and contracts in records and the wallet menu (reverse lookup).
  • QIE Pass: an optional "verified deployer" badge using QIE Pass partner verification (status only, never personal data).
  • Contract console: read and write calls generated from the ABI for deployed contracts.
  • Multi-contract Runbooks: deploy and wire several contracts, proxies and post-deploy calls in one reviewed workflow.
  • CI and API automation: run Runbooks from GitHub Actions with personal access tokens, keeping the wallet signature as a separate approval.
  • Hardened multi-tenant isolation: container-sandboxed test workers and row-level execution locks.
  • Deeper Foundry support: profiles, lib/ submodules beyond forge-std, and library linking.

14Conclusion

4ORGE turns deployment on QIE from a chain of trusted tools into a verifiable workflow: untrusted code is analysed, never executed; builds and dependencies are integrity-checked; tests can gate deployments; people review and sign; and the chain itself is the source of truth for success.

It is live, it has shipped a real, source-verified contract to QIE Mainnet, and it makes QIE's own identity layer, QIE ID, part of the deployment path. The aim is simple: make the safe way to ship on QIE also the fastest.
